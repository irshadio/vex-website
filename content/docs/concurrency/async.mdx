An `async fn` can wait for something, such as a timer, without stopping the rest of the program. While it waits, other tasks and timers on the same isolate run. When the thing it waits for is done, it continues where it left off.

Vex follows Dart here: the result type of an async function is the plain value (`-> string`, not `-> Future<string>`), `await` gives that value, and the whole program runs on one event loop per isolate.

## A first async program

```vex title="fetch.vx"
import "vex:time"

async fn fetch(url: string) throws -> string {
    await time.sleep(100)                   // pauses this function only
    if url == "" {
        throw Error("empty url")
    }
    return "page of {url}"
}

async fn main() throws {
    let page = try await fetch("a.com")     // await gives the value; try handles the error
    println(page)
}
```

```text title="Output"
page of a.com
```

- `async fn` marks a function that may wait. `await` is only allowed inside one, or inside an [async closure](#async-closures).
- `time.sleep(ms)` from [`vex:time`](/docs/stdlib/time) gives a future that completes after `ms` milliseconds.
- An async function that throws needs `try` (or `try?`, or `try ... catch`) at the `await`, like any other throwing call.
- `async fn main()` makes the whole program a task, so `main` can await.

## Tasks and futures

Calling an async function **with** `await` runs it right here, as part of the current task, and gives its value.

Calling it **without** `await` starts it as a new **task** and gives a `Future<T>` right away. The new task runs immediately, up to its first `await` that has to wait, and only then does the caller continue. That is how you run several things at once:

```vex title="start.vx"
import "vex:time"

async fn step(name: string) -> string {
    println("{name}: start")
    await time.sleep(10)
    println("{name}: end")
    return name
}

async fn main() {
    let a = step("a")          // runs until its sleep, then main continues
    let b = step("b")
    println("both started")
    println(await a, await b)
}
```

```text title="Output"
a: start
b: start
both started
a: end
b: end
a b
```

Both sleeps run at the same time, so the program takes about 10 ms, not 20.

### Futures are values

`Future<T>` is a normal type. You can store a future in a variable, a list or a struct field, pass it to functions, and await it any number of times. Awaiting a future that is already done gives its value again without waiting.

```vex title="futures.vx"
import "vex:time"

struct Download {
    name: string
    result: Future<int>
}

async fn size(name: string) -> int {
    await time.sleep(name.len)
    return name.len * 100
}

fn start(name: string) -> Download {
    return Download(name: name, result: size(name))
}

async fn main() {
    let downloads = [start("logo.png"), start("a.txt")]
    for d in downloads {
        println(d.name, await d.result)
    }
    let first = downloads[0].result
    println(await first, await first)
}
```

```text title="Output"
logo.png 800
a.txt 500
800 800
```

`start` is not async, yet it can call `size`: without `await`, an async call is allowed anywhere, because it only starts a task.

The type of a future is written:

| Type | Meaning |
|---|---|
| `Future<int>` | completes with an `int` |
| `Future<void>` | completes with no value, like `time.sleep(ms)` |
| `Future<string, Error>` | completes with a `string` or fails with an `Error` |
| `Future<string, FetchError>` | completes with a `string` or fails with the enum `FetchError` |

Calling a throwing async function without `await` gives the second form: `fetch("a.com")` has the type `Future<string, Error>`. Printing a future shows its type, such as `<Future<int>>`.

## Waiting for several futures

`all` and `any` are built-in functions that take a list of futures.

- `all(futures)` gives a future of every value, in the order of the list. With `[Future<void>]` it gives `Future<void>`. An empty list gives `[]`.
- `any(futures)` gives a future of the first one to settle, whether it succeeded or failed. An empty list stops the program with `any() needs at least one future`.

```vex title="all_any.vx"
import "vex:time"

async fn fetch(url: string, ms: int) -> string {
    await time.sleep(ms)
    return "page of {url}"
}

async fn main() {
    let pages = await all([fetch("a.com", 20), fetch("b.com", 10)])
    println(pages)
    let first = await any([fetch("slow.com", 30), fetch("fast.com", 5)])
    println(first)
    await all([time.sleep(1), time.sleep(2)])
    println("done")
}
```

```text title="Output"
["page of a.com", "page of b.com"]
page of fast.com
done
```

`any` doesn't cancel the others. In the program above, the `slow.com` task is still sleeping when `main` returns, and the program waits for it before it exits (see [When the program ends](#when-the-program-ends)). To stop the ones you no longer need, call [`cancel()`](#cancellation) on them.

A list of futures often comes from `map`. The closure given to `map` can't await, but it can start tasks:

```vex
let urls = ["a.com", "bb.com", "c.io"]
let pages = await all(urls.map(fn(u: string) -> Future<string> => fetch(u)))
```

`all`, `any` and `run` are ordinary names, not keywords: a function of your program with the same name replaces them.

## Errors in async functions

An async function declares `throws` or `throws(E)` like any function. What happens to the error depends on how you call it.

**With `await`**, the error reaches the `await` right away, and you handle it with `try`, `try?` or `try ... catch`:

```vex title="typed.vx"
import "vex:time"

enum FetchError {
    notFound(url: string)
    timeout
}

async fn fetch(url: string, ms: int) throws(FetchError) -> string {
    await time.sleep(ms)
    if url == "missing" {
        throw .notFound(url: url)
    }
    return "page of {url}"
}

async fn main() {
    let f: Future<string, FetchError> = fetch("missing", 5)
    println("started")
    let page = try await f catch e {
        match e {
            notFound(url) => "no page at {url}"
            timeout => "timed out"
        }
    }
    println(page)
    let again = try? await f
    println(again)
}
```

```text title="Output"
started
no page at missing
nil
```

**Without `await`**, the call needs no `try`: starting a task can't fail. The error is stored in the future and comes out wherever the future is awaited, every time it is awaited. A failed future that is never awaited drops its error silently.

```vex title="lost.vx"
import "vex:time"

async fn fail() throws -> int {
    await time.sleep(1)
    throw Error("lost")
}

async fn main() {
    fail()                   // nobody awaits this; its error is dropped
    await time.sleep(20)
    println("main done")
}
```

```text title="Output"
main done
```

**With `all`**, the futures are awaited in list order, and the first failure in that order fails the whole `all`. A later future that fails earlier in time doesn't win: `all` reports it only after every future before it succeeded.

```vex title="all_errors.vx"
import "vex:time"

async fn job(name: string, ms: int, fails: bool) throws -> string {
    await time.sleep(ms)
    println("{name} finished")
    if fails {
        throw Error("{name} failed")
    }
    return name
}

async fn main() {
    let r = try await all([job("a", 30, true), job("b", 10, true)]) catch e {
        println("all:", e.message)
        []
    }
    println(r)
    let s = try await any([job("c", 30, false), job("d", 10, true)]) catch e {
        println("any:", e.message)
        ""
    }
    println(s)
}
```

```text title="Output"
b finished
a finished
all: a failed
[]
d finished
any: d failed

c finished
```

`b` fails first in time, but `a` is first in the list, so `all` fails with `a`'s error. `any` settles with the first future to finish, which is `d`'s failure. The last line comes from task `c`, which keeps running after `main` is done.

**In `async fn main() throws`**, an error that reaches the top is printed as `error: <message>`, with the line it was thrown at and the calls that led there, and exit code 1, but only once every other task and timer is done. The loop finishes its work first:

```vex title="main_error.vx"
import "vex:time"

async fn fail() throws -> int {
    await time.sleep(5)
    throw Error("boom")
}

async fn ticker() {
    for i in 0..3 {
        await time.sleep(10)
        println("tick", i)
    }
}

async fn main() throws {
    ticker()
    let v = try await fail()
    println(v)
}
```

```text title="Output"
tick 0
tick 1
tick 2
error: boom
 --> main_error.vx:5
  at fail (main_error.vx:5)
  at main (main_error.vx:17)
```

The exit code is 1. The `error:` line goes to standard error.

## Cancellation

`f.cancel()` stops the task behind the future `f`. `f.isCancelled` tells whether that happened.

```vex title="cancel.vx"
import "vex:time"

async fn download(name: string, ms: int) -> string {
    println("{name}: start")
    await time.sleep(ms)
    println("{name}: done")
    return name
}

async fn main() {
    let big = download("big", 50)
    let small = download("small", 10)
    big.cancel()
    println(big.isCancelled, small.isCancelled)
    println(await small)
    await time.sleep(60)
    big.cancel()
    small.cancel()
    println(big.isCancelled, small.isCancelled)
}
```

```text title="Output"
big: start
small: start
true false
small: done
small
true false
```

`big` never prints `done`: it stops at the `await` it was waiting at, and the code after it never runs. Cancelling a future that is already done does nothing, so `small` stays done.

### Where a task stops

- A cancelled task stops at its next `await` that waits for a future or a timer. Code between two awaits always runs to the end, so a task never stops halfway through a statement.
- Work that never awaits runs to its end. A new task runs at once up to its first wait, so in the program below the loop is already finished when `cancel()` is called:

```vex title="cancel_late.vx"
import "vex:time"

async fn count(to: int) -> int {
    var n = 0
    for i in 0..to {
        n += 1
    }
    println("counted", n)
    await time.sleep(1)
    println("never")
    return n
}

async fn main() {
    let f = count(1000)
    f.cancel()
    await time.sleep(10)
    println(f.isCancelled)
}
```

```text title="Output"
counted 1000
true
```

### Cancellation spreads

Cancelling a task also cancels every task it started that is still running, and theirs in turn. A task waiting for a cancelled future stops too, so cancellation reaches the code that needed the result:

```vex title="cancel_tree.vx"
import "vex:time"

async fn fetch(name: string, ms: int) -> string {
    await time.sleep(ms)
    println("fetched {name}")
    return name
}

async fn loadScreen() -> string {
    let header = fetch("header", 5)    // started by loadScreen
    let body = fetch("body", 30)
    return "{await header} and {await body}"
}

async fn show(screen: Future<string>) {
    println("showing", await screen)
}

async fn main() {
    let screen = loadScreen()
    let view = show(screen)
    await time.sleep(15)
    screen.cancel()                    // stops loadScreen, body and show
    await time.sleep(40)
    println(screen.isCancelled, view.isCancelled)
}
```

```text title="Output"
fetched header
true true
```

A task that stops because it awaited a cancelled future is cancelled itself, with the tasks it started. In `async fn main`, that ends the program quietly. When the code after an `await` must run, check `f.isCancelled` first.

In code that isn't async, `run` of a cancelled future stops the program:

```text
error: run: the future was cancelled
 --> main.vx:9
```

### Futures without a task

- A future from `time.sleep` can be cancelled too. Tasks waiting for it stop.
- A future from [`isolate.run`](/docs/concurrency/isolates) can be cancelled, which drops its result. The other isolate still finishes its work.

## Timeouts

`time.timeout(f, ms)` from [`vex:time`](/docs/stdlib/time) waits for the future `f` for at most `ms` milliseconds. It gives a future of the value as an optional: the value when `f` finishes in time, otherwise `nil`. When the time runs out, it cancels `f`.

```vex title="timeout.vx"
import "vex:time"

async fn fetch(url: string, ms: int) -> string {
    await time.sleep(ms)
    return "page of {url}"
}

async fn upload(ms: int) throws {
    await time.sleep(ms)
    throw Error("upload failed")
}

async fn main() throws {
    let fast = await time.timeout(fetch("fast.com", 5), 50)
    println(fast)
    let slow = fetch("slow.com", 1000)
    println(await time.timeout(slow, 20) ?? "offline", slow.isCancelled)

    let finished = await time.timeout(time.sleep(5), 50)
    println(finished)

    let sent = try await time.timeout(upload(5), 50) catch e {
        println(e.message)
        false
    }
    println(sent)
}
```

```text title="Output"
page of fast.com
offline true
true
upload failed
false
```

| `f` | `time.timeout(f, ms)` |
|---|---|
| `Future<string>` | `Future<string?>` |
| `Future<string, Error>` | `Future<string?, Error>` |
| `Future<void>` | `Future<bool>`: whether `f` finished in time |
| `Future<string?>` | a compile error |

- Errors from `f` still need `try` at the `await`, as above.
- A future whose value is already optional can't be timed out, since `nil` would be ambiguous. Wrap the value, for example in a record.
- `ms` must be an `int`.

## Streams

A future gives one value. A `Stream<T>` gives any number of values over time, and then ends. There are two ways to make one: a **stream function**, an `async fn` that returns `Stream<T>` and gives each value with `yield`, or a [`StreamController<T>`](#streamcontroller), which other code fills by calling `add`. Either way, `for await` reads the values.

```vex title="ticks.vx"
import "vex:time"

async fn ticks(n: int) -> Stream<int> {
    for i in 0..n {
        await time.sleep(10)
        yield i
    }
}

async fn squares(source: Stream<int>) -> Stream<int> {
    for await x in source {
        yield x * x
    }
}

async fn main() {
    for await t in ticks(3) {
        println("tick", t)
    }
    var sum = 0
    for await s in squares(ticks(4)) {
        sum += s
    }
    println("sum", sum)
}
```

```text title="Output"
tick 0
tick 1
tick 2
sum 14
```

`squares` reads one stream and gives another, so stream functions chain: each value of `ticks(4)` is squared as it arrives.

### Stream functions

An `async fn` whose result type is `Stream<T>` is a stream function. Its body can `await` like any async function, and it gives the values of its stream with `yield value`, where the value must be a `T`.

- **Calling it gives its stream at once, without `await`.** That works in any code, async or not, since nothing runs yet.
- **Its body starts when the stream is first read**, not when it is called.
- **It pauses at each `yield`** until the reader takes the value, then waits there until the reader asks for the next one. A stream function never runs ahead of its reader.

```vex title="lazy.vx"
async fn count(n: int) -> Stream<int> {
    println("start")
    for i in 0..n {
        println("give", i)
        yield i
    }
    println("end")
}

async fn main() {
    let s = count(2)
    println("made the stream")
    for await x in s {
        println("got", x)
    }
    println(s)
}
```

```text title="Output"
made the stream
start
give 0
got 0
give 1
got 1
end
<Stream<int>>
```

The stream ends when the body finishes, or at a bare `return`. A stream function returns no value of its own, so `return x` is a compile error:

```vex title="early_end.vx"
async fn upTo(limit: int, items: [int]) -> Stream<int> {
    for x in items {
        if x > limit {
            return
        }
        yield x
    }
}

async fn main() {
    for await x in upTo(5, [1, 4, 9, 2]) {
        println(x)
    }
}
```

```text title="Output"
1
4
```

- A stream function can't `throw` yet: `async fn f() throws -> Stream<int>` gives `a stream function can't throw yet`. Catch errors inside it, or yield a value that carries the result, such as an enum with a success and a failure case.
- It needs a block body. `=> value` gives `a stream function needs a block body`.
- `yield` works only in the body of the stream function itself, not in a closure inside it. To give values from a callback, use a [`StreamController`](#streamcontroller).
- Methods and generic functions can be stream functions, and a stream function is a value of its type, such as `async fn(int) -> Stream<int>`. See [Streams are values](#streams-are-values).
- A closure can't be a stream function: `async fn() -> Stream<int> { ... }` gives `an async closure can't be a stream function`. A plain closure or function can still return a stream it got elsewhere.

### Reading with for await

`for await x in stream { ... }` runs its body once for each value, waiting between values without blocking the isolate. Other tasks and timers run while it waits. The loop ends when the stream ends.

- `for await` works only in async code: an async function or an async closure.
- The loop variable can be a pattern, as in `for await (n, name) in pairs`.
- A stream has no index, so `for await i, x in s` is an error.
- `for await` needs a `Stream<T>`. A list, map or range takes a plain `for`, and a controller is read through its `stream` member.

**Leaving the loop early stops the stream.** A `break`, a `return` or an error out of the loop body stops a stream function at its next `yield` or `await`, and the code after that point never runs. A stopped stream stays ended, so a later loop over it gets no values:

```vex title="stop.vx"
async fn naturals() -> Stream<int> {
    var i = 0
    while true {
        println("make", i)
        yield i
        i += 1
    }
}

async fn firstOver(limit: int) -> int {
    for await x in naturals() {
        if x * x > limit {
            return x
        }
    }
    return -1
}

async fn check(stop: int) throws {
    for await x in naturals() {
        if x == stop {
            throw Error("hit {x}")
        }
    }
}

async fn main() {
    let s = naturals()
    for await x in s {
        if x == 1 {
            break
        }
        println("got", x)
    }
    for await x in s {
        println("never", x)
    }
    println("first over 5:", await firstOver(5))
    try await check(0) catch e { println(e.message) }
}
```

```text title="Output"
make 0
got 0
make 1
make 0
make 1
make 2
make 3
first over 5: 3
make 0
hit 0
```

`naturals` never ends by itself, yet each loop stops it: after `break`, after `return x`, and after the thrown error.

**A stream has one reader at a time.** Two loops reading the same stream at once stop the program:

```text
error: two loops are reading the same stream; a stream has one reader
 --> readers.vx:9
```

Reading a stream again after a loop has finished with it is allowed. A stream function's stream is ended by then, so the new loop gets nothing. A controller's stream gives the values still queued, as shown below.

### StreamController

`StreamController<T>()` makes a stream that other code fills. It suits values that come from callbacks, such as taps or messages, where a stream function can't `yield`. It needs no import.

| Member | Type | Description |
|---|---|---|
| `StreamController<T>()` | `StreamController<T>` | Makes an open controller with no values. It takes no arguments. |
| `add(value: T)` | `void` | Queues `value` for the reader and wakes it. Never waits. Adding to a closed controller stops the program. |
| `close()` | `void` | Ends the stream once the values already queued are read. Closing again does nothing. |
| `stream` | `Stream<T>` | The stream that gives the added values. It is the same stream each time you read the property. |
| `isClosed` | `bool` | Whether `close()` was called. A property, not a method. |

```vex title="controller.vx"
import "vex:time"

struct Point {
    x: int
    y: int
}

async fn main() {
    let taps = StreamController<Point>()
    let reader = async fn() {
        for await p in taps.stream {
            println("tap at {p.x},{p.y}")
        }
        println("no more taps")
    }
    let done = reader()
    taps.add(Point(x: 1, y: 2))
    taps.add(Point(x: 3, y: 4))
    await time.sleep(5)
    taps.add(Point(x: 5, y: 6))
    taps.close()
    println("closed:", taps.isClosed)
    await done
}
```

```text title="Output"
tap at 1,2
tap at 3,4
closed: true
tap at 5,6
no more taps
```

The reader is a task. It reads the first two points while `main` sleeps. The third point and the close happen without an `await` in between, so `main` prints `closed: true` first; the reader then takes the queued point, sees the end and finishes.

- Values added before anyone reads are kept in order, and a closed controller's queued values are still given before the stream ends.
- When the type of the value can't be inferred, write it: `StreamController()` alone gives `can't tell what the stream carries`. With a declared type, it can be left out: `let words: StreamController<string> = StreamController()`.
- Leaving a loop over a controller's stream early doesn't close it. The values not read yet stay queued for the next loop:

```vex title="queued.vx"
async fn main() {
    let words: StreamController<string> = StreamController()
    for w in ["one", "two", "three"] {
        words.add(w)
    }
    words.close()
    for await w in words.stream {
        println(w)
        if w == "one" {
            break
        }
    }
    for await w in words.stream {
        println("later:", w)
    }
}
```

```text title="Output"
one
later: two
later: three
```

- A loop over a controller that is never closed keeps waiting. If nothing else is left that could add a value, the program ends there, and the code after the loop never runs. Call `close()` when no more values will come.
- Adding to a closed controller is a runtime error:

```text
error: add() on a closed StreamController
 --> taps.vx:8
```

### Streams are values

`Stream<T>` and `StreamController<T>` are normal types. Store streams in variables, fields, lists and optionals, pass them to functions, and return them, from async functions or plain ones. Printing one shows its type, such as `<Stream<int>>` or `<StreamController<int>>`.

```vex title="values.vx"
async fn count(n: int) -> Stream<int> {
    for i in 0..n {
        yield i
    }
}

struct Bag {
    items: [string]

    async fn each() -> Stream<string> {
        for s in items {
            yield s
        }
    }
}

async fn repeat<T>(x: T, n: int) -> Stream<T> {
    for _ in 0..n {
        yield x
    }
}

async fn collect<T>(s: Stream<T>) -> [T] {
    var out: [T] = []
    for await x in s {
        out.push(x)
    }
    return out
}

fn evens(n: int) -> Stream<int> {
    let c = StreamController<int>()
    for i in 0..n {
        c.add(i * 2)
    }
    c.close()
    return c.stream
}

async fn main() {
    let bag = Bag(items: ["x", "y"])
    println(await collect(bag.each()))
    println(await collect(repeat(1.5, 3)))
    println(await collect(evens(3)))

    let make: async fn(int) -> Stream<int> = count
    let sources = [make(2), evens(2)]
    for s in sources {
        println(await collect(s))
    }

    let pairs = StreamController<(int, string)>()
    pairs.add((1, "one"))
    pairs.add((2, "two"))
    pairs.close()
    for await (n, name) in pairs.stream {
        println(n, name)
    }
}
```

```text title="Output"
["x", "y"]
[1.5, 1.5, 1.5]
[0, 2, 4]
[0, 1]
[0, 2]
1 one
2 two
```

- `each` is a stream method and `repeat` a generic stream function. `collect` is an ordinary async function that reads a stream.
- `make` holds the stream function `count` as a value. Calling it gives a stream at once, as calling `count` does.
- `evens` is a plain function: it fills a controller and returns its stream.
- `await` doesn't work on a stream, since a stream gives many values: `await count(3)` gives `await waits for one value, but a stream gives many`.

### Streams and isolates

A stream belongs to the isolate that made it. It can't be copied to another isolate, so a channel can't carry one, and an [`isolate.run`](/docs/concurrency/isolates) closure can't use one:

```text
error: a channel can't carry Stream<int>: it can't be copied to another isolate
 --> chan.vx:6:22
  |
6 |     let ch = Channel<Stream<int>>()
  |                      ^^^^^^^^^^^ send plain values: numbers, strings, lists, maps, structs, enums and channels
```

A closure given to `isolate.run` that uses a stream `s` gives `the closure uses 's', a Stream<int>: it can't be copied to another isolate`. To get values from another isolate as they arrive, receive them from a channel and add them to a controller, or loop on `await channel.receive()` directly.

### Stream errors

Every compile error for streams, with the hint the compiler gives:

## The event loop

Each isolate has one event loop. It owns three queues:

1. **Ready tasks**: tasks whose future settled and that can continue, in first-in, first-out order.
2. **Timers**: futures from `time.sleep`, ordered by when they are due.
3. **Inbox**: messages from other isolates, such as the result of an `isolate.run` or a value sent on a channel that a task is awaiting.

The loop repeats: take the messages that arrived and settle their futures, settle every timer that is due, then run the ready tasks one at a time. When nothing is ready, the thread sleeps until the next timer is due or a message arrives. It doesn't spin.

### What `await` does

`await x` looks at what `x` is:

- **A call of an async function**: the function runs directly, on the current task's stack, like a normal call. Nothing is scheduled. If the function itself never waits, `await f()` costs the same as a plain call.
- **A future**: if it is already done, `await` gives its value (or its error) at once, without giving up the thread. If it is still pending, the current task is put on the future's list of waiters and the loop runs something else. When the future settles, the task goes to the back of the ready queue.

So a task only gives up the thread at an `await` of a pending future. Between two such points, its code runs without interruption, and no other task can see a half-finished state. This is what makes sharing objects between tasks safe without locks.

### Ordering guarantees

These rules are part of how the runtime works, and programs can rely on them:

- **A new task runs first.** Calling an async function without `await` runs it at once, up to its first wait. The caller continues after that.
- **Ready tasks run in the order they became ready.**
- **Waiters wake in the order they started waiting.** If several tasks await the same future, they resume in the order they called `await`.
- **Timers that are due at the same time fire in the order they were created.** `time.sleep(0)` (or any value up to 0) is due at once but still waits for the next turn of the loop, so `await time.sleep(0)` lets every other ready task run first.
- **No preemption.** A task that runs a long loop without awaiting keeps the thread until it finishes or awaits.

```vex title="order.vx"
import "vex:time"

async fn worker(name: string, rounds: int) {
    for i in 0..rounds {
        println("{name} {i}")
        await time.sleep(0)       // let the other task have a turn
    }
}

async fn waiter(name: string, gate: Future<void>) {
    await gate
    println("{name} woke")
}

async fn main() {
    await all([worker("a", 3), worker("b", 3)])

    let gate = time.sleep(10)
    let x = waiter("first", gate)
    let y = waiter("second", gate)
    let z = waiter("third", gate)
    await all([x, y, z])
}
```

```text title="Output"
a 0
b 0
a 1
b 1
a 2
b 2
first woke
second woke
third woke
```

A task that never awaits runs to completion before the code that started it continues:

```vex title="no_preempt.vx"
async fn busy() -> int {
    var n = 0
    for i in 0..1000000 {
        n += i
    }
    println("busy done")
    return n
}

async fn main() {
    let f = busy()
    println("main continues")
    println(await f)
}
```

```text title="Output"
busy done
main continues
499999500000
```

For work like this, use [`isolate.run`](/docs/concurrency/isolates) to move it to another core.

### Timers start when they are created

`time.sleep(ms)` creates its timer when it is called, not when it is awaited. Two sleeps of 50 ms started together finish together:

```vex title="timers.vx"
import "vex:time"

async fn main() {
    let start = time.nanos()
    let timer = time.sleep(50)       // already counting
    await time.sleep(50)
    await timer                      // done by now
    let ms = (time.nanos() - start) / 1000000
    println(ms >= 50, ms < 100)
}
```

```text title="Output"
true true
```

A timer never fires early. It may fire late when the isolate is busy, because a timer can only complete when the loop gets a turn.

## Async from code that isn't async

A plain `fn main()` can start tasks, but it can't `await`. It has two options.

**Let them run after `main` returns.** Tasks started from a plain `main` run up to their first wait, then continue after `main` returns, when the loop starts.

**Wait with `run`.** `run(future)` runs the event loop, including every other task and timer, until that future settles, then gives its value. It needs `try` when the future can fail.

```vex title="sync_main.vx"
import "vex:time"

async fn tick(name: string, n: int) -> int {
    for i in 0..n {
        await time.sleep(2)
        println(name, i)
    }
    return n * 10
}

fn main() {
    println("main starts")
    let background = tick("background", 2)
    let value = run(tick("run", 2))
    println("run gave", value)
    tick("later", 1)
    println("main returns", background)
}
```

```text title="Output"
main starts
background 0
run 0
background 1
run 1
run gave 20
main returns <Future<int>>
later 0
```

While `run` waits, the `background` task makes progress too. `later` only starts its loop after `main` returns.

`run` is for the top of a program, not for async code:

- In an async function, `run` is a compile error: `run waits for the whole loop, so async functions can't use it`. Use `await`.
- A plain function called from async code can't use it either. That is a runtime error: `run can't be used inside async code; use await`.
- If the future can never settle because nothing is left to run, `run` stops the program with `run: the future can never complete, since nothing is left to run`.

## When the program ends

The program ends when `main` has returned (or, for `async fn main`, finished) **and** nothing is pending on the main isolate: no tasks still running, and no futures waiting for another isolate.

- A task that is still sleeping keeps the program alive, and so does the timer it waits for.
- A timer that no task waits for doesn't. `time.sleep(500)` without `await` in a plain `main` doesn't delay the exit.
- A task awaiting `receive()` on a channel keeps the program alive until a message arrives or the channel is closed. If neither ever happens, the program never ends.
- A `for await` loop waiting on a stream doesn't keep the program alive by itself. When nothing else is left to run, the program ends, even if the loop never finished. See [StreamController](#streamcontroller).
- Isolates started with `isolate.spawn` do **not** keep the program alive. See [Isolates](/docs/concurrency/isolates#when-isolates-end).

## Async methods and generics

Methods, static methods, enum methods, interface methods and generic functions can be async:

```vex title="kinds.vx"
import "vex:time"

struct Account {
    balance: int

    async fn deposit(amount: int) -> int {
        await time.sleep(1)
        balance += amount
        return balance
    }

    static async fn open(amount: int) -> Account {
        await time.sleep(1)
        return Account(balance: amount)
    }
}

async fn echo<T>(value: T) -> T {
    await time.sleep(1)
    return value
}

async fn main() {
    let acct = await Account.open(10)
    println(await acct.deposit(5))
    println(await echo("hi"), await echo(4.5))
}
```

```text title="Output"
15
hi 4.5
```

An interface method marked `async` is awaited through the interface like any async call. A struct method that implements it must be async too:

```vex title="store.vx"
import "vex:time"

interface Store {
    async fn find(id: int) -> string?
    fn name() -> string
}

struct MemoryStore: Store {
    users: [int: string]

    async fn find(id: int) -> string? {
        await time.sleep(1)
        return users[id]
    }

    fn name() -> string => "memory"
}

async fn main() {
    let store: Store = MemoryStore(users: [1: "Ann", 2: "Bo"])
    println(await store.find(1), await store.find(9), store.name())
    println(await all([store.find(1), store.find(2)]))
}
```

```text title="Output"
Ann nil memory
["Ann", "Bo"]
```

Leaving out `async` on the struct's method gives `'find' must be async, since it implements Store`.

## Async closures and function values

`async fn(T) -> R` is the type of an async function used as a value. Calling such a value works like calling an async function: `await` gives the result, and a call without `await` starts a task and gives a future.

```vex title="values.vx"
import "vex:time"

async fn fetch(url: string) -> string {
    await time.sleep(5)
    return "page of {url}"
}

fn cached(url: string) -> string => "cached {url}"

async fn twice(load: async fn(string) -> string, url: string) -> string {
    let first = await load(url)
    return "{first}, {await load(url)}"
}

async fn main() {
    let load: async fn(string) -> string = fetch
    println(await load("a.com"))
    let later = load("b.com")
    println(later)
    println(await later)
    println(await twice(fetch, "c.com"))
    println(await twice(cached, "d.com"))
    println(load)
}
```

```text title="Output"
page of a.com
<Future<string>>
page of b.com
page of c.com, page of c.com
cached d.com, cached d.com
<async fn(string) -> string>
```

- A named async function, such as `fetch`, is a value of its async function type.
- A plain function can be used where an async one is expected, as `cached` is above; it simply never waits.
- An async function can't be used where a plain one is expected: `expected fn() -> int, found async fn() -> int`.
- A throwing async function has a type such as `async fn(string) throws -> string`. A call of it without `await` gives `Future<string, Error>`.

### Async closures

A closure is async when it is written `async fn(...)`, or when it is passed or assigned where an async function is expected. Only async closures can `await`.

```vex title="async_closure.vx"
import "vex:time"

struct Button {
    title: string
    onTap: async fn()
}

async fn main() {
    let delayed = async fn(text: string, ms: int) -> string {
        await time.sleep(ms)
        return text
    }
    let slow = delayed("slow", 20)
    let fast = delayed("fast", 10)
    println(await any([slow, fast]))
    println(await slow)

    let square = async fn(x: int) -> int => x * x
    println(await square(7))

    var log: [string] = []
    let save = Button(title: "Save") {
        await time.sleep(5)              // async, since onTap is an async fn()
        log.push("saved")
    }
    await save.onTap()
    println(log)
}
```

```text title="Output"
fast
slow
49
["saved"]
```

A trailing block is async when the parameter it fills has type `async fn()`. An `await` in a closure that isn't async gives `await is only allowed in async closures`, with the hint `mark the closure async: async fn() { ... }`.

### Tear-offs

Async methods tear off like other methods, including interface methods. The result is an async function value bound to the value it was taken from:

```vex
let find = store.find                  // async fn(int) -> string?
println(await all([find(1), find(2)]))
```

[`isolate.run` and `isolate.spawn`](/docs/concurrency/isolates#async-work-on-another-isolate) take async closures and async functions too.

## Embedding the event loop

A program normally runs its own loop after `main`. A host program with its own run loop, such as a game engine or a GUI toolkit written in C, can drive the Vex loop instead by calling this C function, which the runtime exports:

```c
int64_t vex_poll(void);
```

It runs every task that is ready and every timer that is due, then returns the number of milliseconds until the next timer, or `-1` when nothing is pending. While only other isolates can wake the loop, it returns `10`, asking to be called again soon. It must be called on the thread that runs the Vex program. See [C interop](/docs/projects/c-interop).

## Under the hood

- Each task has its own stack of 256 KB, taken from a pool and reused. Switching tasks swaps a few registers, so an `await` deep inside nested calls costs no more than one at the top, and code that doesn't await pays nothing.
- Because a task's stack is smaller than the main thread's, very deep recursion inside an async function overflows sooner. An overflow stops the program with `error: stack overflow: too many nested function calls, probably a function that calls itself without stopping`.
- Async functions need an arm64 or x86-64 CPU.

## Rules and edge cases

- `await` is only allowed in async functions.

  ```text
  error: await is only allowed in async functions
   --> async.vx:5:12
    |
  5 |     return await a()
    |            ^^^^^^^^^ mark the function async: async fn ...
  ```

  In `fn main()`, the hint says `make main async: async fn main()`.

- Only async closures can await: `await is only allowed in async closures`. A closure that isn't async can still start tasks by calling an async function without `await`.
- An async function can't be used where a plain function is expected: `expected fn() -> int, found async fn() -> int`. The other way round works.
- A struct method that implements an async interface method must be async: `'find' must be async, since it implements Store`.
- `extern fn` and `export fn` can't be async.
- `cancel()` takes no arguments, and `isCancelled` is a property: `f.isCancelled()` gives `isCancelled is a property, not a method`.
- `time.timeout` takes a future and an `int`: `time.timeout(5, 10)` gives `time.timeout needs a future, found int`, and a future of an optional gives `time.timeout gives nil when the time runs out, so the future's value can't be optional itself`.
- `await` needs a future or a call of an async function: `await 5` gives `await needs a future or a call of an async function, found int`. A stream gives `await waits for one value, but a stream gives many`.
- `Future` needs its value type: a bare `Future` is `Future needs a type argument`. The error type must be `Error` or an enum: `Future<int, int>` gives `a future fails with Error or an enum, found int`.
- `all` and `any` need a list of futures: `all(5)` gives `all needs a list of futures, found int`.
- A future is not its value. Using one where the value is expected is a type error, such as `expected int, found Future<void>`.
- An awaited throwing call needs `try`: `load can throw, so the call needs try`.
- Futures and streams can't cross between isolates or be sent on channels. See [Isolates](/docs/concurrency/isolates#what-can-be-copied).
- `for await` is only allowed in async code, needs a `Stream<T>`, and has no index. `yield` is only allowed in a stream function. See [Stream errors](#stream-errors) for every stream error.
