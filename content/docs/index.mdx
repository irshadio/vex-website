Vex is a compiled, statically typed programming language. You write `.vx` files, and the `vex` command turns them into native executables through C. It is a general-purpose language: today you can use it for command-line programs, tools and libraries on macOS, Linux and Windows.

<Callout type="warn" title="Early development">
Vex is pre-release (`0.1.0-dev`). The core language is complete and the language for apps is nearly so (phase 2 of the [roadmap](/roadmap), 89 of 97 tasks, with the C interop steps next): the compiler, the standard library, packages and the tools work on macOS, Linux and Windows. Phone apps, editor support and a formatter are planned and not built yet. Expect breaking changes between versions.
</Callout>

## A first look

```vex title="taste.vx"
struct User {
    name: string
    age: int = 18

    fn greet() {
        println("Hi, I'm {name}")
    }

    fn isAdult() -> bool => age >= 18
}

fn main() {
    let users = [
        User(name: "Ann", age: 30),
        User(name: "Sam", age: 15),
    ]

    for i, user in users {
        user.greet()
        println("{i}: adult = {user.isAdult()}")
    }
}
```

```text title="Output"
Hi, I'm Ann
0: adult = true
Hi, I'm Sam
1: adult = false
```

A few things to notice:

- `let` names can't be reassigned and `var` names can. Types are inferred.
- A new line ends a statement, so there are no semicolons. Conditions need no parentheses, and braces are always required.
- Structs are created with named arguments, and fields can have defaults: `User(name: "Sam")` would get `age: 18`.
- Strings interpolate with `{expr}`.
- Methods use fields directly, with no `self.` in front.

## Design goals

Vex aims to be readable at first sight for anyone who knows Dart, Swift, Kotlin, Go or TypeScript, and to be fast and predictable once compiled.

| Goal | What it means in practice |
|---|---|
| Familiar | `let` and `var`, `fn`, `name: Type`, `if` and `for` without parentheses. |
| Low noise | No semicolons, no `self.` inside methods, types inferred where they are obvious. |
| One way to create things | `User(name: "Ann")` builds a struct, and every type is created the same way. There's no `new`. |
| Safe by default | No null: optionals (`T?`) must be checked. Numbers never convert silently. Integer overflow, out-of-range indexes and division by zero stop the program with the source line instead of producing wrong results. |
| Visible failure | A function that can fail is marked `throws`, and every call to it needs `try`. |
| Native speed | Ahead-of-time compilation to machine code, with no virtual machine. Generics are specialized per type, and errors are returned like values, not unwound. |
| Helpful errors | Diagnostics point at the exact spot and suggest a fix. |

## Current status

What exists today:

| Area | State |
|---|---|
| Platforms | macOS and Linux, on arm64 and x86-64 CPUs, and Windows on x86-64. |
| Compiler | Lexer, parser, type checker and C code generator, written in Go. Builds with a C compiler: the SDK includes one on Windows and Linux, and macOS uses the Xcode Command Line Tools. |
| Language | Variables, constants, functions and local functions, closures and trailing blocks, structs with `let` fields, `init` and `copy`, enums with raw values, `match` and patterns, optionals and null-aware elements, errors, generics, interfaces with static requirements, sealed interfaces, extensions of types and interfaces, extension types, records, lists, maps, sets, `Bytes`, ranges and slicing, generators, `repeat`, named loops and `defer`, operator overloading, getters, setters and `didSet`, type aliases, multi-line and raw strings, interpolation format specs and Unicode-aware strings. |
| Concurrency | `async`/`await` with a built-in event loop, and isolates (parallel threads with separate heaps) with channels. |
| Projects | Folders as modules, `pub` visibility, `package.toml`, packages from git with `vex get` and `package.lock`, and building your own C and Objective-C code into a project. |
| Standard library | `vex:math`, `vex:strings`, `vex:time`, `vex:datetime`, `vex:os`, `vex:fs`, `vex:json`, `vex:regex`, `vex:random`, `vex:crypto` and `vex:isolate`. |
| Memory | Automatic, with a generational garbage collector built into every program that scans objects by their exact layout and gives unused memory back to the system. |
| Tools | `vex run`, `build`, `check`, `test`, `get`, `doc`, `doctor`, `emit-c`, `ast`, `tokens`, `version` and `help`, and stack traces in runtime errors. |

What is planned and not built:

| Planned | Notes |
|---|---|
| Phone apps | Cross-compiling the C output for iOS (`arm64-apple-ios`) and Android (the NDK), with native UI from the separate Vex UI framework. |
| Package index | A searchable website of packages in public git repositories. See [Packages](/docs/projects/packages). |
| Tools | Formatter (`vex fmt`), language server, debug adapter and debugger line information, VS Code and JetBrains plugins, `vex new`, `vex repl` and hot reload. |

## How it works

```text
main.vx ─► lexer ─► parser ─► type checker ─► C code ─► clang or gcc ─► native binary
```

The compiler reads your source files, checks them, and writes one C file that contains your program and the Vex runtime (the garbage collector, strings, lists, maps, the event loop and runtime error reporting). It then runs the system C compiler on that file to produce an executable. The result is a standalone binary with no dependency on Vex.

Going through C has practical benefits: the C compiler's optimizer does the low-level work, the same output can later be cross-compiled for phones, and Vex code can call C functions directly with no glue code. You can see the generated C for any program with `vex emit-c`.

Read more in [The compiler](/docs/internals/compiler) and [Generated C](/docs/tools/generated-c).
