This page describes how Vex packages are designed to work: how code names a package, where packages come from, how versions are chosen, and what the package index will do. Most of it is not built yet. Each section says what exists today.

For the practical view of what you can use now, see [Packages](/docs/projects/packages) and [Modules](/docs/projects/modules).

## The idea

A Vex package is a public git repository with version tags. There is no upload step and no central storage: `vex get` will download straight from the repository, and a website will list the packages it knows about.

Code imports a package by its name, and the project file says where that name comes from, as in Dart. Moving a repository then changes one line in `package.toml`, never the imports in your code.

## Imports

There are four forms of import:

| Form | Imports | Example | State |
|---|---|---|---|
| `vex:name` | The standard library, built into the compiler; no download and no project file entry | `import "vex:math"` | Built |
| `"folder"` | A folder of the current project, relative to the importing file | `import "models"` | Built |
| `package:name` | A package listed in the project file | `import "package:charts"` | Planned |
| `package:name/folder` | A folder inside a package | `import "package:charts/line"` | Planned |

A folder is one module: all `.vx` files in it share their names and use each other without imports. Code in another module refers to a name through the module, as in `math.max` or `models.User`, and only names marked `pub` are visible there. Packages will follow the same rules.

Today, a `package:` import is a compile error:

```text
error: package imports aren't supported yet
 --> main.vx:1:8
  |
1 | import "package:charts"
  |        ^^^^^^^^^^^^^^^^ packages arrive with vex get; for now, import folders of this project
```

## Using a package

<Callout type="warn" title="Planned">
`vex get` doesn't exist yet. Running it today prints `vex: unknown command "get"`.
</Callout>

```sh
vex get https://github.com/ann/charts           # the newest tag
vex get https://github.com/ann/charts@0.3.1     # a tagged version
```

`vex get` will add the dependency to `package.toml` under the package's name and record its exact content hash in `package.lock`. `vex run` and `vex build` will fetch whatever is missing, so a fresh clone builds with no extra step.

Downloads will go into one shared cache, `~/.vex/pkg/<repository>@<version>`, rather than a folder inside each project.

## Files

| File | Written by | Purpose | State |
|---|---|---|---|
| `package.toml` | You, and later `vex get` | Package name, version, Vex version, C code, dependencies | Built, except dependencies |
| `package.lock` | `vex get`, never by hand | The exact version and content hash of every dependency, including indirect ones | Planned |

A complete `package.toml` as designed:

```toml
[package]
name = "myapp"
vex = "0.2"

[dependencies]
charts = { git = "https://github.com/ann/charts", version = "0.3.1" }
```

- The key is the name used in `import "package:..."`. It is usually the package's own name from its `package.toml`, and can be changed to resolve a clash between two packages with the same name.
- `path` names a folder inside the repository, for repositories that hold several packages.

What the compiler does with this file today:

- `[package]` accepts `name` (required), `version`, `vex`, `description`, `repository`, `license` and `homepage`. Any other key is an error. `vex` is read but not yet compared with the compiler's version.
- `[c]` accepts `sources`, `libs`, `frameworks` and `flags`; see [C interop](/docs/projects/c-interop).
- `[dependencies]` and `[dev-dependencies]` are accepted and their contents ignored, so a project file written for the package manager already parses.
- Any other section is an error.

The lock file will be committed with the project, so a build that works today builds identically later, and a dependency whose content changed under the same tag will be rejected.

### Why these names and formats

- The name `package.toml` matches `package:` imports and the `[package]` section, the way Dart's `pubspec.yaml` is named after its package tool. `pub.toml` was ruled out because `pub` is a keyword, and `spec.toml` because it doesn't say what it describes.
- TOML is simple, allows comments and has no indentation rules. YAML was ruled out for its indentation mistakes and surprising values (`no` becomes false), and JSON because it allows no comments.

## Publishing a package

<Callout type="warn" title="Planned">
There is nothing to publish to yet. This is how it will work.
</Callout>

1. Put the code in a public git repository with a `package.toml` at the root (or at its `path`).
2. Tag a release: `git tag v0.3.1 && git push --tags`. In a repository with several packages, tags carry the folder: `camera/v0.2.0`.

Versions follow semantic versioning: `v1.4.2` is major, minor and patch, and a new major version may break code that uses the package.

## Choosing versions

When two packages need different versions of a third, Vex will pick the lowest version that satisfies all of them: minimal version selection, as in Go. A build never picks up a newer release by itself; versions change only when someone runs `vex get`.

A build holds one version of each package, so packages that need different major versions of the same dependency can't be used together, as in Dart.

## Official packages

Where a package made by the Vex project lives depends on what it needs:

| Kind | Where | Imported as |
|---|---|---|
| Useful to every program | The standard library, inside the compiler | `vex:math`, `vex:strings`, `vex:time`, `vex:os`, `vex:fs`, `vex:isolate` today; `vex:http` and `vex:json` planned |
| Everything else | Its own public git repository | `package:name` (planned) |

Official repositories will live in a GitHub organization rather than a personal account. `vex new` will write their entries into `package.toml`, and the website will list them first.

## The package index

<Callout type="warn" title="Planned">
The package index website isn't built.
</Callout>

A searchable index of packages. It stores no code.

- **Listing.** A package appears when someone submits its repository, when `vex get` fetches it for the first time, or when its repository has the `vex` topic on GitHub.
- **Pages.** README, versions, license, dependencies and the packages that use it, the `package.toml` line to copy, and API docs generated from `///` comments by `vex doc`.
- **Scores.** Whether it compiles with the current Vex, has docs and tests, which platforms it supports, and how widely it is used.

If the website is down, `vex get` still works, because it talks to git directly.

## Later: cache and checksum log

Once Vex has outside users:

- **Cache.** A server that keeps a copy of every published version, so a project still builds if the author deletes the repository or GitHub is unreachable.
- **Checksum log.** A public, append-only record of every version's hash, so nobody can quietly replace the code behind an existing tag.

Both will be optional for `vex get`, which can always fall back to git.

## Order of work

1. Modules: folders as modules, imports of project folders and `vex:` libraries, `package.toml`. **Done.**
2. `vex get` and `package.lock`, fetching `package:` dependencies from git.
3. `vex doc`, which the website reuses.
4. The package website.
5. The cache and the checksum log.
