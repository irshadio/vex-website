`vex` is the compiler and toolchain in one command. It checks Vex source, translates it to C, calls a C compiler to build a native executable, and can run the result right away. It also fetches packages, writes API documentation and checks the tools it builds with. This page documents every subcommand as of version `0.1.0-dev`.

## Overview

```text
vex <command> [arguments]
```

| Command | What it does |
|---|---|
| [`vex run [flags] [file or folder] [-- args]`](#vex-run) | Compile and run a program |
| [`vex build [file or folder] [-o out] [flags]`](#vex-build) | Build a native executable |
| [`vex emit-c [file or folder]`](#vex-emit-c) | Print the generated C code |
| [`vex check [file or folder]`](#vex-check) | Check a program for errors without building it |
| [`vex test [file or folder] [flags]`](#vex-test) | Run the program's tests |
| [`vex get [flags] [repo[@version]]...`](#vex-get) | Add dependencies and lock their versions |
| [`vex doc [path] [name]`](#vex-doc) | Show or write the API documentation |
| [`vex doctor [-v]`](#vex-doctor) | Check the tools Vex builds with |
| [`vex ast <file>`](#vex-ast) | Print the syntax tree of one source file |
| [`vex tokens <file>`](#vex-tokens) | Print the tokens of one source file |
| [`vex version`](#vex-version) | Print the Vex version |
| [`vex help [command]`](#vex-help) | Show help |

There are no global flags other than `-h`/`--help` (the same as `vex help`) and `-v`/`--version` (the same as `vex version`).

## File mode and project mode

`run`, `build`, `check`, `test` and `emit-c` take a target, which is either a source file or a project folder.

| Target | Mode | What is compiled |
|---|---|---|
| `app.vx` | File mode | That one file, plus the folders and `vex:` modules it imports. Other `.vx` files next to it are not included. |
| `store` (a folder) | Project mode | The project in that folder. It must contain a `package.toml`. |
| nothing | Project mode | The project in the current folder. |

In project mode, the top folder of the project is the root module and holds `main`; every subfolder is a module of its own. A folder without `package.toml` is refused, with the lines to add:

```text
vex: no package.toml in emptyproj; create one with:

[package]
name = "emptyproj"
```

Project structure and `package.toml` are covered in [Modules and projects](/docs/projects/modules).

## vex run

```text
vex run [flags] [file or folder] [-- args]
```

Compiles the program, builds it in a temporary folder, runs it, and deletes the executable afterwards.

| Flag | Effect |
|---|---|
| `--debug` | Compile without optimizations and with debug information (`-O0 -g`) instead of `-O3` |
| `--sanitize=list` | Build in sanitizers that stop the program at memory and other errors: `address`, `undefined` and `thread`, comma-separated |

The flags must come before the program; anything after the program goes to it. See [Build modes](#build-modes).

```sh
vex run --debug args.vx one     # built with -O0 -g; os.args() is ["one"]
vex run args.vx --debug         # an optimized build; os.args() is ["--debug"]
vex run --sanitize=address,undefined app.vx
```

```sh
vex run hello.vx            # a single file
vex run                     # the project in the current folder
vex run store               # the project in store/
```

The program's standard input, output and error are connected to the terminal, so `input()` and pipes work as usual:

```sh
printf 'Ann\n' | vex run ask.vx
vex run report.vx > report.txt
```

Compile errors are printed and nothing runs. If the program builds, `vex run` exits with the program's own exit status.

### Passing arguments to the program

Everything after the target goes to the program, where [`os.args()`](/docs/stdlib/os#args) returns it. A `--` right after the target is removed, so you can pass arguments that start with `-`:

```sh
vex run app.vx one two          # os.args() is ["one", "two"]
vex run app.vx -- -v            # ["-v"]
vex run -- -v                   # the current project, with ["-v"]
vex run store -- x              # the project in store/, with ["x"]
```

The first argument counts as the target only when it ends in `.vx` or names an existing folder. Otherwise `vex run` runs the project in the current folder and passes every argument to it, so `vex run report x` runs the current project with `["report", "x"]`. Use `--` to make this explicit.

Only the first `--` is removed: in `vex run app.vx a -- b`, the program receives `["a", "--", "b"]`.

### When the program is stopped by a signal

If the program is ended by a signal, `vex run` exits with 128 plus the signal number, as shells do. For an interrupt (Ctrl-C), a closed pipe, `SIGTERM` or `SIGHUP` it prints nothing extra. For other signals it adds a line:

```text
vex: the program was killed
```

```text
vex: the program crashed (abort trap); this is a bug in vex
```

The second message means the generated program crashed in a way the runtime didn't catch; runtime errors such as an index out of range or a stack overflow print their own message instead and exit with status 1. See [Runtime errors](/docs/tools/runtime-errors).

## vex build

```text
vex build [file or folder] [-o out] [flags]
```

Builds a native executable and prints its path.

| Flag | Effect |
|---|---|
| `-o out` | Where to write the program (default: its name) |
| `--traces` | List the calls that led to a runtime error; on with `--debug` |
| `--debug` | Compile without optimizations and with debug information (`-O0 -g`) instead of `-O3`, and keep the generated C next to the program as `<out>.c` |
| `--sanitize=list` | Build in sanitizers that stop the program at memory and other errors: `address`, `undefined` and `thread`, comma-separated |

Flags can come before or after the target. See [Build modes](#build-modes) for `--traces`, `--debug` and `--sanitize`.

```sh
vex build hello.vx
```

```text title="Output"
Built hello
```

| Target | Default output name |
|---|---|
| `hello.vx` | `hello`: the file name without `.vx`, and `hello.exe` on Windows |
| `src/app.vx` | `app` |
| a project | the `name` from `package.toml` |

The executable is written to the current folder, not next to the source: `vex build src/app.vx` creates `./app`.

`-o` sets the output path. It can come before or after the target:

```sh
vex build src/app.vx -o tool        # ./tool
vex build -o bin/tool src/app.vx    # bin/tool
```

- If the output names an existing folder, the executable goes inside it with the default name: `vex build -o bin hello.vx` writes `bin/hello`. This is also why building a project from its parent folder, `vex build store`, writes `store/store` when the project is named `store`: the default output `store` is the project folder itself.
- The folder for the output must already exist. A missing folder makes the C compiler's linker fail.
- `vex build` refuses to overwrite the source file, which could happen with a source file that has no `.vx` extension:

```text
vex: building would replace the source file h; choose another name with -o
```

The executable is self-contained: the runtime and garbage collector are compiled into it, and it depends only on the C library and the system math and thread libraries. Copy it to another machine with the same operating system and CPU architecture and it runs there. Built with the Linux SDK's toolchain, it is a static executable that runs on any x86-64 Linux, whatever its C library. There is no cross-compilation option yet.

Builds are optimized with `-O3` unless `--debug` is given. A plain build leaves [stack traces](/docs/tools/runtime-errors#stack-traces) out, since recording each call slows down programs made of many small calls; add `--traces` to keep them.

## vex check

```text
vex check [file or folder]
```

Parses and type-checks the program without generating C or calling the C compiler. It is the fastest way to see compile errors, for example from an editor.

```sh
vex check hello.vx
```

```text title="Output"
hello.vx: no errors
```

With no target it checks the project in the current folder and prints `.: no errors`. When there are errors, it prints them to standard error and exits with status 1. See [Compile errors](/docs/tools/compile-errors).

## vex test

```text
vex test [file or folder] [flags]
```

Builds the program with its `test` blocks and `_test.vx` files, runs every test, each in its own process, and prints a line for each and a summary. The executable is built in a temporary folder and deleted afterwards.

| Flag | Effect |
|---|---|
| `-filter text` | Run only the tests whose names contain `text` |
| `--debug` | Compile without optimizations and with debug information (`-O0 -g`) instead of `-O3` |
| `--sanitize=list` | Build in sanitizers that stop the program at memory and other errors: `address`, `undefined` and `thread`, comma-separated |

Flags can come before or after the target.

```sh
vex test                        # the project in the current folder
vex test math.vx                # the tests in one file
vex test -filter parse          # only tests whose names contain "parse"
```

```text title="Output of vex test"
✓ adds two numbers
✗ parses a list
  math_test.vx:7: expect(xs.len == 2)
    two items
    left:  3
    right: 2

2 tests: 1 passed, 1 failed
```

The exit status is 0 when every test passed or there are none, and 1 when a test failed, `-filter` matched nothing, or the program doesn't compile. [Testing](/docs/tools/testing) covers test blocks, `expect`, the output format and the rules in full.

## vex emit-c

```text
vex emit-c [file or folder]
```

Prints the C code that `vex build` would compile, to standard output. The output is one self-contained C file: the runtime library first, then your program after a `// --- Program ---` line.

```sh
vex emit-c hello.vx > hello.c
cc -std=gnu11 -fwrapv -w -pthread -O3 hello.c -o hello -lm
```

`emit-c` leaves test blocks out, like `vex build`.

[Generated C](/docs/tools/generated-c) explains how each Vex construct appears in it.

## vex get

```text
vex get [--path folder] [repo[@version]]...
```

Adds packages to the project and locks the exact versions of everything it depends on. A package is a git repository with version tags such as `v0.3.1`.

```sh
vex get https://github.com/ann/charts           # the newest tag
vex get https://github.com/ann/charts@0.3.1     # that version
vex get https://github.com/ann/charts@0.3       # the newest 0.3.x
vex get --path camera https://github.com/vex-lang/packages   # a package in a folder, tagged camera/v0.2.0
vex get                                         # download what package.toml lists and lock it again
```

| Flag | Effect |
|---|---|
| `--path folder` | The folder of the package, for repositories that hold several packages, each tagged `folder/vX.Y.Z` |

Each repository is added to the `[dependencies]` of `package.toml` under the name the package gives itself, and the version, commit and content hash of every package, including the ones those packages use, are written to `package.lock`. With no repositories, `vex get` downloads what `package.toml` lists and writes `package.lock` again. It runs the system `git`, so `git` must be installed; [`vex doctor`](#vex-doctor) checks for it.

`vex run`, `vex build`, `vex test` and `vex check` then use exactly the versions in `package.lock`, downloading any that are missing from the cache. [Packages](/docs/projects/packages) covers versions, the lock file and the cache in full.

## vex doc

```text
vex doc [file, folder or vex:module] [name] [-o dir] [--text]
```

Writes or prints the API documentation of a program, a project or a standard module, from its [`///` doc comments](/docs/tools/doc).

| Flag | Effect |
|---|---|
| `-o dir` | Where to write the HTML pages (default: `doc`) |
| `--text` | Print an overview to the terminal instead of writing HTML |

```sh
vex doc                      # HTML pages in doc/, one per module, and an index
vex doc shapes -o site       # the project in shapes/, written to site/
vex doc --text               # an overview in the terminal
vex doc Circle               # one declaration's signature and doc comment
vex doc Circle.area          # a member
vex doc vex:json Json        # the standard library too
```

With a name, `vex doc` prints that declaration, as `--text` does. Only `pub` declarations are documented, except in a root module that has none, such as a program of one file, where all are. See [API docs](/docs/tools/doc).

## vex doctor

```text
vex doctor [-v]
```

Checks the tools Vex builds with and says how to install what is missing. It never installs anything itself.

```text title="Output of vex doctor"
Doctor summary (to see all details, run vex doctor -v):
[✓] Vex (0.1.0-dev+11b0009)
[✓] C toolchain - builds Vex programs (Apple clang 21.0.0)
[✓] git - downloads packages for vex get (git 2.50.1)
[✓] Xcode - builds iOS apps (Xcode 26.4)
[!] Android toolchain - builds Android apps (NDK 29.0.13113456)
    ! Java 11.0.26 is too old; Android builds need JDK 17 or newer
      Set $JAVA_HOME to Android Studio's JDK

! Doctor found issues in 1 category.
```

| Check | Needed for |
|---|---|
| Vex | The version, and the standard library built into `vex` |
| C toolchain | Building any program. On macOS it also looks for `swiftc`, which programs that import `vex:crypto` need |
| git | Downloading packages with `vex get` |
| Xcode (macOS only) | Building apps for iPhone and iPad, in the coming UI framework |
| Android toolchain | Building Android apps: the Android SDK, the NDK and JDK 17 or newer |

| Flag | Effect |
|---|---|
| `-v`, `--verbose` | Show where each tool was found, such as which C compiler was chosen and whether it came with the Vex SDK, and more details |

Only a missing or broken C toolchain is an error, with exit status 1. Problems with git, Xcode and the Android tools are warnings with a line saying how to fix them, and the exit status stays 0, so `vex doctor` can run in scripts and CI.

## vex ast

```text
vex ast <file>
```

Parses one source file and prints its syntax tree. It only parses: it doesn't resolve names, check types or follow imports, so it works on files that would fail `vex check`. It takes exactly one file, not a project folder.

```vex title="tiny.vx"
fn main() {
    let name = "Vex"
    println("Hi {name}")
}
```

```sh
vex ast tiny.vx
```

```text title="Output"
file
  fn main
    block
      let name
        "Vex"
      call
        println
        interp
          "Hi "
          name
```

## Build modes

`vex build`, `vex run` and `vex test` build an optimized program by default. Three flags change that:

| Flags | C compiler flags added |
|---|---|
| none | `-O3` |
| `--debug` | `-O0 -g` |
| `--sanitize=list` | `-O3 -fsanitize=list -fno-sanitize-recover=all -fno-omit-frame-pointer -g` |
| `--debug --sanitize=list` | `-O0 -g -fsanitize=list -fno-sanitize-recover=all -fno-omit-frame-pointer` |

### --traces

`--traces` keeps [stack traces](/docs/tools/runtime-errors#stack-traces) in a `vex build`, so a runtime error lists the calls that led to it. The program stays fully optimized; recording each call costs some speed in programs made of many small calls. `vex run`, `vex test` and `--debug` builds always have traces, and a plain `vex build` leaves them out.

```sh
vex build --traces app.vx
```

### --debug

`--debug` turns off optimizations and adds debug information, so a debugger such as lldb or gdb can show every variable and step line by line. With `vex build`, the generated C is also kept next to the program as `<out>.c`, and debug information points into it:

```sh
vex build --debug app.vx
```

```text title="Output"
Built app
Kept the C code in app.c
```

```sh
vex build --debug args.vx -o bin/tool
```

```text title="Output"
Built bin/tool
Kept the C code in bin/tool.c
```

On macOS, clang also writes the debug information into a folder next to the program, such as `app.dSYM`. If `<out>.c` would be the source file itself, the build stops with `vex: keeping the C would replace <file>; choose another name with -o`. [Generated C](/docs/tools/generated-c#debugging) explains how to find your code in the C file.

`vex run --debug` and `vex test --debug` build the same way, in a temporary folder that is deleted afterwards.

### --sanitize

`--sanitize` builds in the C compiler's sanitizers, which check the program as it runs and stop it with a report at the first problem. It takes a comma-separated list of:

| Sanitizer | Finds |
|---|---|
| `address` | Reads and writes outside an allocation, use after free and other memory errors |
| `undefined` | Undefined behaviour in C, such as a misaligned pointer or a shift out of range |
| `thread` | Data races between threads |

Vex code itself is checked by the runtime, so the sanitizers are mainly useful for C code called through [`extern fn`](/docs/projects/c-interop). `thread` can't be combined with `address`, and a name that isn't in the list is refused; both are usage errors, with exit status 2:

```text
vex: unknown sanitizer "memory"; use address, undefined, thread
```

```text
vex: the thread sanitizer can't be combined with address
```

A program built with `address` doesn't report memory leaks: the garbage collector owns the heap, so every report would only list its memory. Which sanitizers work depends on the C compiler and the system. Here a C function writes past the end of an allocation:

```c title="native/sum.c"
#include <stdint.h>
#include <stdlib.h>

int64_t sum_first(int64_t n) {
    int64_t *xs = malloc(4 * sizeof(int64_t));
    for (int64_t i = 0; i < n; i++) xs[i] = i;
    int64_t total = 0;
    for (int64_t i = 0; i < n; i++) total += xs[i];
    free(xs);
    return total;
}
```

```vex title="main.vx"
extern fn sum_first(n: int) -> int

fn main() {
    println(sum_first(8))
}
```

With `sources = ["native/sum.c"]` in the `[c]` section of `package.toml`, `vex run` prints `28` and exits normally, hiding the bug. `vex run --sanitize=address` stops at the bad write (the report is trimmed here):

```text title="Output of vex run --sanitize=address"

WRITE of size 16 at 0x603000001c20 thread T0
    #0 0x0001041ee858 in sum_first sum.c:6
    #1 0x0001041e9d04 in main main.c:3472
```

On macOS the sanitizer ends the program with an abort signal, so `vex run` adds its crash line and exits with status 134; the bug here is in the C code, as the report shows. Under `vex test`, the report goes to standard error and the test fails with `crashed with signal 6`.

### VEX_CFLAGS and CC

`VEX_CFLAGS` adds flags to every C compile, after the build-mode flags, so they win when they conflict: `VEX_CFLAGS="-O2" vex build app.vx` builds with `-O2`. `CC` picks the C compiler. Both are described under [Environment variables](#environment-variables).

## Exit codes

| Code | Meaning |
|---|---|
| 0 | Success. For `vex run`, the program exited with 0. For `vex test`, every test passed or there were none |
| 1 | Compile errors, a file that can't be read, a missing `package.toml`, or a C compiler failure. For `vex test`, a failed test or a `-filter` that matched nothing. For `vex get`, a repository or version that can't be found. For `vex doctor`, a C toolchain that can't build programs |
| 2 | Usage error: an unknown command, an unknown flag, a missing `-o` or `-filter` value, too many targets, or a bad `--sanitize` list |
| any | `vex run` passes on the program's exit status: 1 after a runtime error or an error escaping `main`, the value given to `os.exit`, or 128 plus the signal number |

Usage errors print the command's usage line:

```text
vex: unknown command "biuld"
Run 'vex help' for a list of commands.
```

```text
flag needs an argument: -o
Usage: vex build [file or folder] [-o output] [--traces] [--debug] [--sanitize=list]
```

```text
flag provided but not defined: -fast
Usage: vex run [--debug] [--sanitize=list] [file or folder] [-- args]
```

```text
flag needs an argument: -filter
Usage: vex test [file or folder] [-filter text] [--debug] [--sanitize=list]
```

Flags take one dash or two, and a value can follow `=` or a space: `-o app`, `--o=app`, `-filter=parse` and `--filter parse` all work.

## Environment variables

### Read by the compiler

| Variable | Effect |
|---|---|
| `CC` | The C compiler to use, which may be a full path with spaces or include arguments, such as `CC="clang -v"`. When unset, `vex` uses the clang of the [Vex SDK](/docs/install), in `toolchain/bin` next to the folder of the real `vex` binary, then the first of `clang`, `cc` and `gcc` found on the `PATH`. `vex doctor -v` shows which one was chosen. |
| `VEX_CACHE` | Where `vex get` and builds keep downloaded packages (default: `~/.vex/pkg`). |
| `VEX_CFLAGS` | Extra flags for the C compiler, split at spaces and added after the default and build-mode flags, so they can override them, for example `VEX_CFLAGS="-march=native"`. |
| `NO_COLOR` | When set to any non-empty value, diagnostics are printed without color. Color is also off when standard error isn't a terminal. |

If no C compiler is found, every build fails with:

```text
vex: no C compiler found; install clang (on macOS: xcode-select --install) or set $CC
```

The C compiler is called with `-std=gnu11 -fwrapv -w -pthread`, then the [build mode](#build-modes) flags (`-O3` by default), then `VEX_CFLAGS`, then the flags from the `[c]` section of `package.toml`, the output and the generated C file, the sources, libraries and frameworks from the `[c]` section, and finally `-lm`. `-fwrapv` defines what `&+`, `&-` and `&*` do on overflow, and `-w` hides warnings about the generated code. See [C interop](/docs/projects/c-interop) for the `[c]` section.

When the C compiler fails, `vex` says whose fault it is likely to be:

| Message starts with | Likely cause |
|---|---|
| `the C compiler (...) failed; check the C code and the [c] section of package.toml` | The project's own C code or flags |
| `linking failed: a C function named by an extern isn't defined` | An `extern fn` whose C code isn't linked |
| `the C compiler (...) failed on generated code; this is a bug in vex` | Anything else, which usually is a compiler bug |

### Read by programs

Every Vex program, whether run with `vex run` or built, reads these when it starts:

| Variable | Effect |
|---|---|
| `VEX_GC_STATS` | When set to anything other than `0`, prints a garbage collector summary to standard error when the program ends. |
| `VEX_GC_STRESS` | A number `n`: runs a collection every `n` allocations, every fourth one major. Very slow; used to test the collector. |
| `VEX_GC_VERIFY` | When set, checks at each minor collection that no write barrier was missed. Used with `VEX_GC_STRESS` to test the collector. |

```sh
VEX_GC_STATS=1 vex run cycles.vx
```

```text
gc: 7 collections, 31250 KB allocated, 4096 KB peak heap, 2578 KB live, 4160 KB from the system, 4160 KB at most, 0 KB given back
```
